# NOOR — Climate Intelligence and Heatwave Response System

**See the risk. Save lives.**

NOOR is a Python **desktop application** (Tkinter) that helps decision-makers understand heat
risk, find the people most exposed, plan cooling, water and medical resources, and test
"what if" heatwave scenarios. It follows one workflow:

**Climate data → Risk analysis → Vulnerability assessment → Early warnings → Resource planning → Scenario comparison**

Everything runs locally from a SQLite file. No internet connection is needed after the
three libraries are installed, and every method is plain Python you can read and change.

> **Demonstration data.** The district "Saptapur", its 16 wards and every population,
> vulnerability, resource and weather figure in the bundled database are **synthetic**
> (generated by `noor/seed.py` with a fixed random seed). The app says so in the header
> and sidebar. They are not IMD observations, and no live weather feed is connected.
> NOOR supports preparedness; it does not replace warnings from the India Meteorological
> Department (IMD), State Disaster Management Authorities or local officials.

## Technology stack

| Layer | Technology | Used for |
| --- | --- | --- |
| Programming language | Python 3.12+ | Application and business logic |
| Desktop GUI | Tkinter + ttk | Window, sidebar navigation, forms, tabs (`ttk.Notebook`) |
| Database | SQLite (`sqlite3`) | Locations, observations, resources, risk results, alerts, plans |
| Data processing | Pandas | Filtering, grouping and validating climate data |
| Numerical computing | NumPy | Normalisation, weighted averages, statistics, demo data |
| Data visualisation | Matplotlib | Charts embedded in the window with `FigureCanvasTkAgg` |
| Table interface | `ttk.Treeview` | Climate records, alerts, resources, results |
| Testing | Python `unittest` | Logic, database and GUI tests |
| Data input/output | CSV | Importing observations, exporting reports |

`requirements.txt` lists only numpy, pandas and matplotlib; everything else is in Python's
standard library.

## Install and run (Windows)

**Easiest:** double-click **`Start NOOR.bat`**. The first time, it creates a private Python
environment in `.venv` and installs the three libraries (needs internet once, about a minute).
After that it opens NOOR straight away, offline.

**By hand:**

```bash
py -3.12 -m venv .venv
.venv\Scripts\activate
python -m pip install -r requirements.txt
python app.py
```

(Any Python 3.12 or newer works. On macOS/Linux use `python3 -m venv .venv`, then
`source .venv/bin/activate`.)

| Command | What it does |
| --- | --- |
| `python app.py` | Open the application window |
| `python app.py --init` | Create the database (and the demo data on a first run), then exit; safe to repeat |
| `python app.py --reset` | Delete the local database, rebuild the demo data, then open the window |

The first start creates `instance/noor.db`. A splash screen is shown while it is prepared.

## Screens

| Screen | What it does |
| --- | --- |
| **Overview** | Monitored locations, high-risk count, active alerts, available resources, latest observation; risk-distribution chart; a situation summary written from the numbers; locations by risk; recent activity |
| **Climate Monitoring** | Observations table with location, date-range and text filters, NumPy summary statistics and CSV export; daily trend chart per location (missing days marked); all-location temperature heatmap; per-location comparison and monthly means; **CSV import** with row-by-row validation ("check only" or import) |
| **Risk Assessment** | Score, category, confidence and the four dimensions for every location; filters; click a location for the reasons, the recommended response (from its open alerts), a dimension chart and every indicator used; what-if weights preview (not saved) |
| **Alerts** | Alerts from the rule engine with severity, location, reason, trigger vs threshold, period, recommended actions and creation time; filters; **Acknowledge** and **Mark resolved** (saved in SQLite, never backwards); run the rules again; CSV export |
| **Resource Allocation** | Inventory of five resource types; change status and amount, **reassign to another location**, delete, add; run the greedy planner (risk-first or population-first) with demand, served, unmet and coverage; compare the two strategies; save and list plans; CSV export |
| **Scenario Lab** | Temperature increase, longer hot spell, new cooling centres, water and medical capacity, budget and staff; reruns the real risk and allocation code on a background thread and shows before/after numbers, a chart, tables and a plain-language explanation; CSV export |
| **Reports & Analytics** | Summary statistics and tables (risk by region, alerts by severity, resources by type, location comparison); nine charts with PNG export; the project's SQL queries with their results; six CSV reports with provenance headers |
| **Data Management** | Database file, row counts per table, every data source and its kind; list of locations; add a location |

Keyboard: **Ctrl+1 … Ctrl+8** switch screens, **F5** reloads the current one, and every
control can be reached with Tab. Column headings sort the tables when clicked.

## How the parts work together

1. `app.py` opens `NoorApp` (Tkinter). A background thread runs `NoorService.setup()`: it
   creates the tables from `schema.sql` and, on a fresh database, loads the demo data
   (`seed.py`), calculates risk, runs the warning rules and saves two plans.
2. Each screen is a `Page` subclass. Screens only call `NoorService` / `Database` methods and
   the chart functions; they contain no SQL and no maths of their own.
3. `NoorService` loads `Location` and `Resource` objects from SQLite, and passes them to the
   engines: `RiskEngine` (risk.py), `WarningEngine` (alerts.py), `AllocationPlanner`
   (allocation.py) and `Scenario` (scenario.py). Results are saved back to SQLite.
4. Charts are Matplotlib `Figure` objects shown with `FigureCanvasTkAgg`; the same figures can
   be saved as PNG. Reports are CSV text from Pandas DataFrames.
5. Slow jobs (first start, scenarios, imports, recalculation) run on a background thread with
   its own database connection; the result is handed to the window through a `queue.Queue`,
   so the window never freezes. Errors are shown in a message box and the status bar,
   never as a crash.

## Database

SQLite file `instance/noor.db` (override with the `NOOR_DB_PATH` environment variable). Eight
tables: `data_sources`, `regions`, `locations`, `observations`, `resources`,
`risk_assessments`, `alerts`, `allocations`. Foreign keys are switched on, every query uses
`?` placeholders, observations are unique per location, date and type, and alerts are unique
per location, rule and period, so running the rules again never duplicates them. Data
survives restarts. See [docs/DATA_DICTIONARY.md](docs/DATA_DICTIONARY.md).

## Limitations

- All bundled data is synthetic; no live feed (IMD or other) is connected. Real data can be
  imported as CSV, for example model-derived weather from Open-Meteo via
  `scripts/fetch_open_meteo.py` (the only part that uses the internet, and only when you run it).
- Thresholds, weights and planning rates are NOOR defaults, not official criteria, and have not
  been validated against health outcomes. Scores are relative priorities, not predictions.
- The allocation planner is a transparent greedy rule, not an optimiser.
- The map is a schematic grid, not real geography.
- Designed for laptop and desktop screens (minimum window 1180 × 700).
- There is no login: anyone who can open the app on the computer can change its data.
